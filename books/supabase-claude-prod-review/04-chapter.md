BとしてAのメモを更新したのに、エラーが出ませんでした。これは権限の不具合でしょうか。それとも、正しく拒否できたのでしょうか。答えを出すには、レスポンスと、Aから見たメモの状態を合わせて調べます。

**この章の到達点：** 許可の試験と拒否の試験を組にし、操作前後のデータから結果を判定できる。

## 管理者として読めることは、利用者の試験にならない

管理用のSQLエディターや特権キーでデータを取得しても、一般利用者のアクセス制御が正しいとは判断できません。アプリが使う経路で、A、B、未ログインの状態を切り替えます。

教材では、AとBがそれぞれ自分のメモを一件作ります。テスト対象のメモIDを記録し、後の操作がその行へ向いていることを確かめます。IDを間違えて存在しない行を調べると、拒否の試験が誤って成功したように見えるからです。

## 許可と拒否を対にする

| 番号 | 操作 | 期待結果 | 追加の確認 |
| --- | --- | --- | --- |
| 1 | 未ログインで読む | データを取得できない | レスポンスに本文が含まれない |
| 2 | 未ログインで作る・更新・削除する | 各操作が拒否される | 対象行が変わらない |
| 3 | Aが自分のメモを作る | 一件作成される | Aで再取得して内容一致 |
| 4 | Aが自分のメモを読む | 対象の一件を取得 | Bのメモを含まない |
| 5 | Aが自分のメモを更新する | 対象行が変わる | 再取得した内容が一致 |
| 6 | AがBのメモIDを指定して読む | Bの本文を取得できない | 一覧・詳細の両方を試す |
| 7 | AがBのメモを更新する | Bの行が変わらない | Bで元の内容を再取得 |
| 8 | AがBのメモを削除する | Bの行が残る | Bで対象IDを再取得 |
| 9 | Aがowner_idをBとして作成する | 拒否される | Bに新しい行が増えない |
| 10 | Aが自分のowner_idをBへ変更する | 列権限で拒否される | Aで元の所有者と内容を確認 |
| 11 | Aが自分のメモを削除する | 対象行が消える | 作成済みの行を対象にする |
| 12 | Bが自分のメモを操作する | 設計どおり許可される | Aだけに依存する実装でない |

この表の「作る・更新・削除」は、それぞれ独立して実施します。試験回数を数えるときも分けます。さらに、ID・作成日時の挿入や更新が拒否されること、空文字・501文字の本文や未定義のstatusが保存されないことを確認します。所有者の行を削除する試験は、ほかの試験が終わった最後に行います。

## HTTPの成功と業務の成功を分ける

RLSによって対象行が見えなければ、SELECTやUPDATEがエラーを出さず、対象ゼロ件になる場合があります。アクセス拒否が常に同じHTTPステータスになるとは限りません。[公式資料](https://supabase.com/docs/guides/database/postgres/row-level-security)

そのため、更新の成功試験では「エラーがない」だけで合格にしません。対象行が本当に変更されたかを確かめます。拒否の試験では、対象ゼロ件だけでなく、正当な所有者から見て元の行が残っていることも確認します。

また、更新APIが特権キーを使っている場合には、データベース側の試験とは別にAPIの認可を試します。アプリの画面でボタンを隠していても、直接APIを呼ばれたときの保護にはなりません。

## 配布パッケージのDB単体試験を再実行する

[読者向け教材をダウンロード](https://github.com/ponponpon888/supabase-claude-book-materials/archive/refs/heads/main.zip)し、展開して使います。[教材の説明と最新版](https://github.com/ponponpon888/supabase-claude-book-materials)も参照できます。

コマンドは、展開先の`package.json`があるフォルダーで、一行ずつ実行します。Windows PowerShellでは`npm.cmd`を使います。Windows 11／PowerShell 5.1／Node.js 24.13.0で、依存パッケージのインストール、DB単体38項目、無料9章・記事1本のZenn構造・HTML確認が成功しました（2026年11月4日）。


正常終了の目印は、終了コード0と、JSON内の`total: 38`、`passed: 38`、`failed: 0`です。結果は`evidence/rls-report.json`にも保存されます。これは今回の版の件数であり、将来の版では増減します。

| 項目 | 今回確認した範囲 |
| --- | --- |
| 実行環境 | Linux／Node.js v24.22.1、およびWindows 11／PowerShell 5.1／Node.js v24.13.0。PGlite 0.5.14、PostgreSQL 18.6 |
| SQL | 第3章に掲載したSQLを直接取り込んで実行 |
| 正常系 | A/Bそれぞれの作成・取得・更新・削除 |
| 拒否 | 未ログイン相当、他人の行、所有者の偽装、禁止列の変更 |
| 制約 | 本文の長さ・NULL、未定義の状態値 |

試験内の`auth.users`と`auth.uid()`は、認可条件を調べるための簡略化した代用品です。実際の認証サーバーを再現したものではありません。試験が用意する`auth`スキーマやロールのSQLをSupabaseへコピーしないでください。

故障を検出できることを確かめるため、試験中だけRLS等を意図的に緩めます。これは外部接続を持たないメモリー内DBだけの操作です。教材の検証済み表示を、本番やホスト環境の動作保証へ広げないようにします。

## 実際のアプリで確認するときの操作例

次のJavaScriptは、既にログイン処理があるアプリへ当てはめるための例です。`clientA`と`clientB`は、別々の通常ユーザーとして認証されたクライアントを指します。秘密キーや管理者クライアントは使いません。このHTTP経路の例は今回未実行です。

```javascript
// uidAはAの認証済みユーザーID。固定文字列を実ユーザーと取り違えない。
const created = await clientA.from('book_tasks')
  .insert({ owner_id: uidA, summary: 'Aの検証用メモ' })
  .select('id, owner_id, summary, status').single();
if (created.error) throw created.error;
const memoId = created.data.id;

const updated = await clientA.from('book_tasks')
  .update({ summary: 'Aが変更したメモ' })
  .eq('id', memoId).select('id, summary');
if (updated.error || updated.data?.length !== 1 ||
    updated.data[0].summary !== 'Aが変更したメモ') {
  throw new Error('Aの更新結果が期待と異なります');
}

const attempted = await clientB.from('book_tasks')
  .update({ summary: 'Bによる変更' })
  .eq('id', memoId).select('id, summary');
if (attempted.error || attempted.data?.length !== 0) {
  throw new Error('Bの拒否結果が期待と異なります');
}

const after = await clientA.from('book_tasks')
  .select('id, summary').eq('id', memoId).single();
if (after.error || after.data?.summary !== 'Aが変更したメモ') {
  throw new Error('拒否後のデータが期待と異なります');
}
```

複数クライアントを同じブラウザーで使う場合は、保存先のセッションが共有され、AのつもりがBに切り替わっていないか確認します。独立したブラウザープロファイルや、セッション保存先を分けた検証環境で、操作直前に利用者を照合します。クライアント作成・ログイン方法は、使用中のSDKの公式資料に合わせてください。[公式資料](https://supabase.com/docs/reference/javascript/auth-signinwithpassword)

## 自動化しても、観測するものは変わらない

自動テストに移すときも、操作前の状態、操作者、対象ID、期待結果、操作後の状態を固定します。DBのポリシー試験と、実際の認証・APIを通した試験は役割が異なります。前者は権限条件を細かく確かめ、後者はアプリの接続や認証情報の渡し方も含めて確かめます。

テストの認証情報は検証用に限定し、ログへアクセストークンを出しません。結果を共有するときは、架空データとアカウントの役割だけで再現できるようにします。

## 記録を読んで、判定してみる

次は演習用の架空記録です。`memo-A`は、Aが直前に作成して再取得した一件を指す説明用ラベルで、実際のUUIDではありません。

| 記録 | 操作 | 観測結果 | 判定 |
| --- | --- | --- | --- |
| A | Aが`memo-A`を更新 | エラーなし、更新対象0件 | 正常系は不合格。更新できていない |
| B | Bが`memo-A`を更新 | 対象0件。直後にAが元の本文を取得 | この拒否試験は合格 |
| C | Bが存在未確認のIDを更新 | 対象0件 | 試験準備が不足。拒否を確認した証拠にできない |
| D | Bが`memo-A`を更新 | 応答前に通信が切れた。再取得は未実施 | 結果不明。拒否成功とは判定しない |

記録Bも、それだけでBの権限すべてが正しいとは言えません。Bが自分のメモを更新できる正常系を合わせると、「Bの操作が何もかも止まっているだけ」という故障を見つけられます。

## 想定と違ったときの調べ方

正常系が失敗したら、まず操作者、環境、対象IDを照合します。次に返されたエラーや件数から、接続、GRANT、列権限、ポリシーのどこを調べるか絞ります。RLSを無効にして動かすことを、正常系の合格条件にはしません。

他人の行が見えた場合は、試験を止めて取得経路を確認します。A/Bのセッションが混ざっていないか、特権クライアントを使っていないか、広く許可する別のポリシーがないかを調べます。修正後は、拒否の試験と本人の正常系を再実施します。

**章末の作業：** 実アプリの検証環境がある場合は、章の冒頭の12項目を個別の操作に分けて実施し、「実測結果」「対象環境」「対象の版」「確認日時」を追記する。DB単体試験だけを行った場合は、その結果と未確認のHTTP経路を分けて記録する。環境がない場合は、試験計画を作り、実測欄を未確認のまま残す。

## 演習：ゼロ件の意味を判断する

Bの更新結果はゼロ件でした。試験後にAで読んだ本文は元のままですが、B自身のメモも更新できません。どこまで合格と言えますか。

:::details 解答例と判断の理由
存在と操作者が正しい前提なら、Aの行がBに変更されなかったという拒否試験は合格です。しかしBの正常操作は不合格なので、権限全体は合格にできません。セッション、接続先、GRANT、更新列、ポリシーを調べ、修正後に正常系と拒否系を両方やり直します。
:::
