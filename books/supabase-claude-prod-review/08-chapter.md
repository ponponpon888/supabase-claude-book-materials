権限を試し、変更手順を書き、復旧の準備も調べました。最後に、その証拠が「これから公開する版」にそろっているかを確認します。過去のテスト結果を、今回の合格と取り違えないための仕上げです。

**この章の到達点：** 対象の版と証拠を照合し、公開するか保留するかを理由付きで記録できる。

ここまでに作った表を、一回の公開作業へまとめます。長く使えるチェックリストにするには、各項目に証拠への参照欄を付けます。チェックが付いた理由を、翌週の自分や別の担当者がたどれるようにするためです。

## 公開前

- [ ] 対象のコミット・変更内容・公開先が一致している。
- [ ] 開発、検証、本番の接続先を確認した。
- [ ] 秘密値がブラウザー、公開ソース、ログに入っていない。
- [ ] GRANT、RLS、ポリシー、特権経路を確認した。
- [ ] A/B/未ログインの許可・拒否試験を実施した。
- [ ] 更新の成功を、実際の変更内容で確認した。
- [ ] ビルドと必要なテストが、公開対象の版で成功した。
- [ ] DB変更の順序・影響・中止条件が決まっている。
- [ ] 戻せる範囲と、戻せないデータ変更を把握している。
- [ ] 通知先や外部サービスの接続先が対象環境と一致する。
- [ ] 未確認事項を記録し、公開判断に反映した。

## 公開直後

- [ ] 実際の公開URLで主要ページを開ける。
- [ ] 新しいセッションでログインできる。
- [ ] 管理された確認用アカウントで主要操作を完了できる。
- [ ] 保存した内容を再取得して確認した。
- [ ] 公開したアプリの版とmigrationの適用状態を確認した。
- [ ] エラーと処理時間に想定外の変化がない。
- [ ] 確認に使ったデータを、記録したIDの範囲で整理した。

本番での確認用操作は、業務データや顧客へ影響しない範囲を先に決めます。A/Bの破壊的な試験や負荷試験は、通常は分離した検証環境で行い、本番では承認された範囲のスモークテストを行います。

## 翌日・運用中

- [ ] 失敗した処理と、結果不明の処理を確認した。
- [ ] 通知待ちや処理待ちが長く残っていない。
- [ ] 利用者の問い合わせに、公開後の変化がないか確認した。
- [ ] 使用量や費用に想定外の増加がない。
- [ ] 対応が必要な項目へ、担当者と次の行動を付けた。

## 一回分の公開記録

```text
公開日時：
対象アプリ・URL：
対象コミット：
適用migration：
確認した主要操作：
検証記録：
公開直後の結果：
残っている課題：
切り戻しの判断と手順：
翌日の確認結果：
```

この記録があれば、次の変更で何をもう一度確かめるべきかが見えてきます。確認項目は運用しながら育てます。毎回同じ失敗が起きるなら、チェックの追加だけでなく、仕組みで防げる場所を探しましょう。

無料部分を読み終えた時点で、すべての欄が埋まっている必要はありません。未確認の場所を明確にし、影響の大きいものから確かめていく。その進め方を、自分のアプリの運用に持ち帰ってください。

## 演習：最終課題：公開判断を一枚にする

次の架空の証拠を読み、公開・保留の判断、理由、次に必要な確認を記録してください。

| 証拠 | 記録の内容 |
| --- | --- |
| 公開対象 | r18。変更は権限SQLとメモ編集画面 |
| ビルド | r18で成功 |
| A/B試験 | r17で合格。r18ではAの保存だけ確認 |
| Bの追加試験 | r18で存在未確認のIDを指定し、結果ゼロ件 |
| 切り戻し | アプリの戻し方は記録済み。今回のDB変更との互換性は未確認 |

:::details 解答例と判断の理由
この教材の公開基準では保留です。権限SQLを変えたr18でのA/B試験が不足し、存在未確認のIDでは拒否の根拠になりません。r18で作成・再取得した行を使い、本人の正常操作と他人の拒否を確認します。DB変更後に旧アプリを動かせるかも検証します。証拠がそろったら、未確認を合格に書き換えるのではなく、実測結果を追記して公開判断を更新します。
:::
